Tape block measurements — 2026-08-16
====================================

Host: Apple Silicon (darwin 25.5.0), Release build, -O2.
NOTE: this is a HOST measurement. The Raspberry Pi 4 figure the spec asks for
is still outstanding; it needs a Buildroot cross-build (Docker) and was not run.
The ratio against the RAT is recorded because the RAT already ships and runs on
the Pi at the same 8x oversampling, so it transfers better than the absolute
host number does.

Per-sample cost, 48 kHz, one stereo block instance
--------------------------------------------------
  RAT    1010.4 ns   4.85% of one host core   (mono core, result copied to both channels)
  Tape   2300.7 ns  11.04% of one host core   (two independent oversampled lanes)
  Tape / RAT ratio: 2.28x

Per oversampled lane the tape block is about 1.14x the RAT, so most of the
difference is that tape runs two lanes where the RAT runs one. A mono-input
preset therefore pays twice for identical lanes; collapsing that is the first
optimisation to reach for if the Pi figure comes back over budget, ahead of
dropping to 4x oversampling.

Reading of the four voicing checks the plan lists:
  1. No level jumps. 0.57 dB across the whole drive range on real playing,
     which is the calibration holding on program material and not just a sine.
  2. No brittle top end. Relative HF content FALLS 1-2 dB as drive rises.
  3. No low-end mud at high drive. Relative LF content does not grow with
     drive (-3.20 dB at 12, -3.68 dB at 24).
  4. Drive 0 and drive 24 are plainly different. Crest factor collapses from
     18.98 dB to 11.24 dB — 7.7 dB of peak eaten — which is tape compression.

These were measured, not listened to. The subjective pass is still owed.
No TapeHysteresis::Parameters were changed: the default fit passed every
objective check, so there was nothing to tune away from.
